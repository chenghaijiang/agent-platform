# ADR-014：统一智能工作台与智能体可选

- 状态：已接受
- 日期：2026-11-14
- 关联：ADR-011/012/013（见 `../../2026/docs/adr/`，本仓库外）、ADR-008（术语模型四元裁决）
- 来源：grill-with-docs 审问第一轮裁决（Q1–Q6 全部按推荐方案接受）

> 注：ADR-001~013 存放于 `../2026/docs/adr/`（仓库外），本目录自 ADR-014 起承载本仓库演进决策。

## 背景

用户诉求：「智能问答页面能选智能体吗？希望这个聊天框升级成个人工作台，能调用智能体的能力」。

现状事实（代码勘察）：

- 智能问答域（`src/agent_platform/chat/`）是单一固定 RAG 图（检索 → 生成 → 引用溯源 → Guardrails），UI「当前应用」为写死文案，无可选智能体概念；
- AgentDesk 域（`src/agent_platform/agentdesk/`）是独立功能域（计划确认 → 工具执行 → hunk 评审 → commit 门禁），独立页面 `/agentdesk.html` 新窗口打开，与聊天框零交集；
- 数据层只有 `AgentTask`（意图容器），无「智能体」实体——「能选智能体」现状为否，需新设计。

## 决策

1. **智能体 = Agent Profile（能力预设包）**：一组可被选中的配置 = system prompt + 工具集 + 执行图模板，类似 GPTs 的预设形态。用户自建智能体为后续扩展（Profile 上加管理面），第一期只做内置预设（如「知识问答助手」「代码工程师」）。
2. **统一工作台（分阶段）**：聊天框升级为唯一入口；Agent 执行的计划确认、工具审批、执行进度以消息卡片形式出现在同一聊天流内，`/agentdesk.html` 分阶段退役。第一期先做到「聊天流内看任务进度 + 计划确认/审批卡片」，hunk 评审与 commit 门禁第二步迁入。
3. **会话级绑定**：一个会话绑定一个智能体（创建时选定），换智能体 = 开新会话。理由：与现有 `chat_session` ↔ `thread_id`（checkpointer 分库分责）一一映射兼容，避免跨图 state 迁移。默认智能体 = 知识问答助手，现有会话零迁移。
4. **审批/治理呈现 = 结构化卡片消息**：聊天流插入审批卡片（按钮交互即 resume 图），SSE 推送卡片状态变化。消息模型扩展为 `type: text | agent_event | approval_card`。否决自然语言指令 resume（payload 校验脆弱）与弹窗审批（违背工作台形态）。
5. **第一期验收线**：选智能体 + 对话驱动执行 + 执行事件流（工具调用/输出）以消息展示 + 计划确认/审批卡片。能完整走通「发一句话 → 智能体干活 → 审批 → 出结果」闭环。hunk 评审/commit 门禁不在第一期。
6. **前端继续无框架 vanilla**（HTML/JS 渲染函数），不引入构建链；卡片类型膨胀失控再议。

### 术语裁决（并入 glossary）

「智能体」（用户可感知、聊天框可选）与 v0.2 术语表「Agent 应用」（控制面抽象：绑定模型策略、Prompt、知识库、工具、Guardrail）**为同一概念的两个视角**：Agent Profile 是 Agent 应用在渠道层的落地实体。UI 文案用「智能体」，文档与代码标识用 `agent_profile`，禁造第三名。

## 后果

**正面**：

- 聊天框成为个人工作台，问答（RAG）与执行（AgentDesk）两个孤岛域在用户视角合一；
- 会话级绑定保住 checkpointer 语义，现有 QA 会话零迁移成本。

**负面/风险**：

- 事件协议需从「SSE delta + citations」升级为多类型消息信封（后续 ADR 裁决）；
- `/agentdesk.html` 双页面并存的过渡期，前端需维护两套渲染逻辑；
- 智能体能力全景（Agent Loop / Hooks / Subagent / Memory / Teams 等 20 项）分期未决，归下一轮审问裁决。
